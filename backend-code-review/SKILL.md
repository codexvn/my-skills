# 后端代码风格评审

## 评审流程

1. **确定对象**：先确认评审范围（未提交 diff、某次提交、分支对比、指定文件）；用户未指明时先查看工作区状态与最近提交再确认。
2. **建立双基线**：把代码分成两类——本次新增或重写的代码（硬性要求零豁免），与本次仅触碰的存量代码（只要求不扩大旧模式，不要求回改历史）。判断依据是新增行落在新建文件还是既有文件。
3. **逐维度检查**：按下面九个维度过一遍；与 diff 无关的维度跳过，并在报告中注明未覆盖；第九节在 diff 涉及埋点、模型调用或异步链路时检查。
4. **输出发现清单**：按「阻塞 / 应改 / 建议」三级输出，每条包含位置（文件与行号）、问题描述、依据条目、修改方向。存量基线内的问题不报。
5. **回答收口三问**：报告末尾必答。

## 一、提交纪律

- 提交信息遵循 Conventional Commits（`type(scope): 动宾描述`），scope 表达功能域而非文件路径，语言与格式跟随项目既有提交约定；带工单号时按项目格式附加。
- diff 只含本次需求必需改动：无顺手格式重排、无与本次无关的「顺便优化」、无调试日志与注释掉的代码残留。
- diff 与新增日志不含密钥、连接串、内部地址、用户隐私数据。

## 二、代码整洁

### 函数

- 新方法单一职责、处于同一抽象层级，长度以一屏（约 50 行）为理想、100 行为上限；不新增 lint 豁免标记来绕过长函数约束。【硬性】
- 在存量豁免区（已带 lint 关闭标记的代码段）内只做本次必需的最小修改，不在豁免区内扩大改动面。【硬性】
- 参数个数以 5 个以内为目标；避免 boolean 参数控制函数行为分支，拆成两个语义明确的方法。【硬性】
- 名字里只承诺查询的方法不写库、不改共享状态。【硬性】

### 命名

- 用领域动词表达业务意图，不用 process、handle 一类无信息量动词。【风格】
- 同一概念只用一种表示：值集合一律用枚举，不新增枚举与字符串常量双轨并存的代码。【硬性】
- 既有领域缩写只在已使用范围内沿用，新概念起完整名。【风格】

### 注释

- 注释只写代码无法表达的内容（为什么、约束、边界、外部协议要求），不复述代码行为。【硬性】
- JavaDoc 要么补全参数与返回值说明，要么删掉空标签。【硬性】
- 行内注释符号后统一加空格；生产注释不含「首版」「暂时实现」「预留」等研发过程信息。【硬性】
- TODO 写明具体问题与处理方向。【硬性】

### 重复与表达

- 复制既有代码段前先检查是否已存在分叉的孪生副本；同构代码第三处出现才提取公共方法。【风格】
- 刻意的防御性重复模板（如逐回调的隔离 try-catch）不当作重复代码要求收敛。【风格】
- 公共方法返回具体类型，不用 Object 让调用方做类型判断分流；不同协议形态（如流式与普通响应）拆成不同端点。【硬性】
- 数值阈值、上限、时间窗口用具名常量并附注释，不写裸数字。【风格】
- 死代码直接删除，不保留「以防万一」。【硬性】

### 类与数据组织

- 新类 JavaDoc 首句写明职责边界（「负责 X；Y 由 Z 提供」的句式）。【风格】
- 一个类的注入依赖出现三簇以上互不相关的职责时，先拆类再继续写功能。【风格】
- 嵌套类型优先静态嵌套类；仅单个实现内部使用的类型用私有内部类型，不扩大公共 API。【硬性】
- 不为单一字段或一次调用创建没有独立语义的顶层类；纯转发方法内联。【硬性】

## 三、架构分层

### 依赖方向

- 纵向链路只允许两条：Controller → Service → Repository，以及 Service → Integration/Gateway；模块间依赖不反向。【硬性】
- 模型对象（Entity / DTO / VO / Form）不依赖任何上层。【硬性】
- 共享实体与仓储归最低合理共享层级，应用私有实现留在应用模块。【硬性】

### 各层职责

- Controller 只做协议转换、参数校验、鉴权与响应组装；流式装配、业务 ID 生成、异步任务提交一律下沉 Service。【硬性】
- Service 承担业务规则、编排与事务边界；跨多个仓储或外部能力的流程在 Service 组织。【硬性】
- Repository 只做持久化读写，不含业务规则；可增长数据的列表查询分页，不做全量加载内存过滤。【硬性】
- 外部 SDK（模型服务、对象存储、消息、命令执行等）一律收敛到 Integration/Gateway 边界，外部协议类型不泄漏进业务方法签名；外部客户端已在多个业务类散布直接使用时，新增一处即按阻塞处理。【硬性】
- 事件监听层不 import 具体业务实现类，只依赖抽象基类或事件接口。【硬性】
- 不新建只做查询转发的薄包装服务层；既有薄包装层不要求回改，但不再扩大。【硬性】

### 依赖注入

- 注入方式跟随项目主流风格，不混用多种注解；字段命名不带实现类后缀。【硬性】
- 可选依赖显式声明，并在使用前显式检查或以注释声明降级行为。【风格】
- 不通过静态上下文或运行时 Bean 查找（服务定位器）隐藏依赖——存量存在时视为已知债，新代码禁止。【硬性】
- 自建线程池与执行器有命名工厂与明确 owner，销毁路径覆盖正常结束、异常与取消。【硬性】

## 四、防御与异常

- 对外部回调或钩子的每次调用单独 try-catch 隔离，失败记日志后继续主链路——保持这一模式，不要求收敛。【风格】
- 宽泛 catch 之后必须先记日志（带异常对象）再包装为项目业务异常重抛；禁止空 catch、吞异常继续、返回 null 掩盖非法状态。【硬性】
- 不新增「把异常消息当日志消息」的写法（消息可能为空、可能被误当格式串）；用固定消息加键值对、异常对象放末位。【硬性】
- 错误码用细分段，不再新增一律用通用错误码的写法。【风格】
- 判空用工具类方法，不手写判空链；上游契约已保证的数据不逐层重复判空；集合与查询结果区分「无结果」「尚未加载」「执行失败」。【硬性】
- 所有外部调用（模型、命令执行、HTTP、存储）显式传超时，超时值来自配置或常量而非内联数字。【硬性】
- 异步结果等待必须带超时。【硬性】
- 边界失败的处理方向分清：对可预期失败转为对端可读的输入继续流程，面向用户的失败抛业务异常——两种路径不混用。【风格】
- 有停止语义的流程遵循三件套：停止标志 + 状态落库到终态 + 异常路径也置终态。【风格】
- 权限判定默认拒绝；不经默认值、异常回退或静默降级扩大权限。【硬性】

## 五、接口契约

- 路由前缀与资源命名跟随项目约定并保持一致；写操作与查询的 HTTP 方法语义化。【硬性】
- 响应统一信封；仅流式与文件流例外；不新增裸返回。【硬性】
- 请求绑定方式跟随项目主流，不在 Controller 手工解析 JSON 字符串字段。【硬性】
- 接口文档注解齐全：分组说明、操作说明、字段说明与示例值，示例值必填。【硬性】
- 鉴权身份从项目统一上下文获取，不自行解析请求头。【硬性】

## 六、事务与持久化

- 事务注解写在实现类方法上，写操作带全异常回滚，只读标记只读语义。【硬性】
- 删除策略跟随项目约定；逻辑删除的批量语句保留租户条件；物理删除属需确认项。【硬性】
- 仓储继承项目统一基类；动态条件用参数化惯用法，不拼字符串；更新语句带修改标记。【硬性】
- 新实体跟随项目模板实体的注解组合、主键与业务 ID 策略、租户字段语义。【硬性】
- 绕过 ORM 写原生 SQL 属需确认项；确需时做多数据库方言适配。【硬性】

## 七、日志

- 日志消息语言跟随所在模块既有分工，同一消息内标点统一。【风格】
- 完整对话、完整响应一类大对象默认级别不输出，只在排障开关下输出。【风格】
- 关键路径（状态流转、外部调用、写操作）必有留痕；warn/error 带足以定位的键值。【硬性】
- 敏感数据不入日志。【硬性】

## 八、测试与收口

- 非平凡逻辑（分支、循环、解析、金额、权限路径、公开 API）同批带可运行测试；断言验证行为而非凑覆盖率。【硬性】
- 新增测试方法用行为句式命名；不为测试向生产代码加无业务意义的公共方法。【硬性】
- 触及接口的改动做本地链路冒烟，结果记入变更说明。【硬性】
- 提交前跑过对应模块的 lint 与测试；CI 红禁止合并。【硬性】
- 交付附变更说明：做了什么（对照验收标准）、关键决策与理由、风险与未尽事项、验证方式。【硬性】

## 九、可观测性与链路埋点（OpenTelemetry）

### 收敛与降级

- 埋点代码收敛在统一门面：公共基座（tracer 获取、父上下文管理、span 收尾）加按业务线的门面类；业务代码只调语义化入口（按轮次、按工具、按节点开启 span），不直接使用追踪 API 在业务类里散埋。【硬性】
- 埋点全程可降级：无 agent 注入时全局入口返回空实现、指标库缺失时仅记 span 属性；降级行为写进类注释，业务代码不感知埋点存在，埋点永不抛错影响主链路。【硬性】
- 可选的指标依赖在门面字段上注明可空语义（如「无指标环境时仅记 span」），不通过运行时判空掩盖装配错误。【风格】

### span 生命周期纪律

- start 与 end 由同一拥有方配对，end 在 finally 统一执行避免双重结束；异常路径先记录异常再置 ERROR 状态。【硬性】
- 写入 span 的异常文本经过截断上限（防长异常消息撑爆 span 与后端存储）。【硬性】
- 跨回调的层级传递不依赖标准 Scope（回调返回后 Scope 已失效）：经显式父上下文传递——单线程顺序流程用公共基座的父 span 栈进出作用域，并行任务由提交线程捕获父上下文后传给工作线程。【硬性】
- ThreadLocal 类父栈必须有泄漏兜底：最外层收尾时清理残留（结束残留 span 保留时序供排查、清栈、告警提示存在未配对收尾），使残留止于本次执行，不污染线程池中该线程的后续链路。【硬性】

### 属性与数据红线

- 属性命名双轨：优先使用开放语义约定的标准属性（如生成式 AI 约定的用量、模型、操作名），自定义指标带模块前缀避免与标准属性冲突。【风格】
- 敏感数据红线：模型输入输出全文、凭证、用户隐私不进 span 属性与指标；该红线作为约束写进埋点门面的类注释。【硬性】
- 计时指标覆盖关键延迟分解：首包时间、生成时长、吞吐速率与输入输出用量，而不是只记总耗时。【风格】

### 日志与链路同源

- span 收尾时在关闭作用域之前输出本地摘要日志（日志行自动携带本轮链路标识），使本地日志与远端链路同源——没有链路后端时也能从日志看到调用概况。【风格】
- 异步与线程池执行传递链路上下文（trace 标识 / 日志诊断上下文），跨线程不丢；异步任务开头补全上下文、结尾恢复。【硬性】

## 输出格式

发现清单按三级输出，每条包含位置（文件:行）、问题描述、依据条目、修改方向：

- **阻塞**：违反任一【硬性】条目，必须修复后才能合并。
- **应改**：风格与结构问题，本次或最近跟进修复。
- **建议**：可选优化，不阻塞。

存量基线内的问题（本次未触碰，或属既有模式且本次未扩大）不进入清单，最多在报告开头用一句话概述已知债。

## 收口三问

1. 这次改动让系统更清晰还是更混乱——是收敛已知债（统一外部边界、细分错误码）还是新增债务（新的散布、新的豁免区）？
2. 三个最常见失分点确认过没有：外部调用不经统一边界、在 lint 豁免区内扩大改动、异常日志写法违规？
3. 变更说明是否写全？
